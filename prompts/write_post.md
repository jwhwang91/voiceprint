# 지시서: 사진 분석 + 글·배치 작성 (Claude Code 수행 · 모델 Opus 4.8)

## 목표
1) 사용할 사진을 **직접 보고 분석·태깅**하고,
2) 페르소나 말투로 **약 2000자(한국어)** 분량의 본문을 쓰고,
3) 각 사진을 **내용에 맞는 위치**에 배치한다.

> 모델: `.claude/settings.json` 의 기본 모델이 **Opus 4.8** 이어야 한다(사진 비전 분석 +
> 페르소나 모사 품질). 더 약한 모델로 실행 중이면 멈추고 사용자에게 알린다.

## 입력
- `personas/<글종류>.md` — 적용할 페르소나 (종류는 description/사진으로 추론하거나 확인)
- `data/input/<job>/photos/**` — 사용할 사진. 보통 **카테고리 폴더로 분류**되어 있다(예:
  `photos/메뉴/`, `photos/사시미 플레이트 2인/`, `photos/내부/`). **파일명·순서에만 의존하지 말고 내용을 직접 확인**하되,
  **폴더 이름은 사용자가 직접 분류한 강한 카테고리 힌트**이므로 태깅 근거로 적극 활용한다.
  - ⭐ **영상(MOV/MP4)이 섞여 있을 수 있다.** 영상은 사진처럼 직접 열지 말고(토큰 낭비), 먼저
    `python main.py video-scan --job "<job>"` 로 추출된 **썸네일 프레임**만 본다. 상세는 **§2.5**.
- `data/input/<job>/description.txt` — 사용자가 적은 방문 메모 **(선택 — 없을 수 있음)**
  - **있으면**: 사진으로 알 수 없는 사실(정확한 메뉴명·가격·방문 맥락·강조점)의 **근거**로 삼는다.
  - **없으면(사진만 있는 경우)**: 멈추지 말고 아래 **§0 비전 단독 모드**로 사진만 보고 글을 완성한다.
- 배치도 스키마: `src/blog_automation/content/schema.py` 의 `LAYOUT_SCHEMA`
- `data/drafts/<job>/SEO_BRIEF.md` — ⭐ **SEO 전략 브리프 (선택 — 있으면 반드시 반영)**
  - SEO 레이어(`python main.py seo-generate-brief --job "<job>"`)가 미리 만들어 둔, 검색 유입을
    높이는 **Primary/Secondary 키워드·추천 제목·태그·검색 의도** 전략이다. **있으면 읽고 따른다.**
  - ⚠️ **우선순위(절대)**: ① 사진/영상에서 **확인되는 사실** → ② **페르소나 말투/구조** →
    ③ SEO_BRIEF 의 키워드/제목/태그 전략 → ④ 자연스러운 네이버 문체. SEO 는 ①②를 **절대 깨지 않는다**.
  - 키워드는 **억지로 반복하지 말 것**(제목 1회·첫 문단 1회·소제목 1회·본문 각 1~2회면 충분).
    추천 제목은 **권고**다 — 페르소나 톤에 맞게 자연스럽게 다듬어 써도 된다. 사진/영상과 맞지 않는
    키워드(예: 주차 정보 없는데 '주차', 실사용 안 한 제품 '내돈내산')는 **넣지 않는다**(브리프의 Avoid 참고).
  - 브리프가 **없으면** 기존대로 진행한다(SEO 없이 페르소나 글쓰기). 멈추지 말 것.

## 절차

### 0. 입력 모드 판별 (메모 유무)
`data/input/<job>/description.txt` 가 **있고 비어있지 않으면** → 메모를 **사실 근거**로 삼아 진행.
**없거나 비어 있으면** → ⭐ **비전 단독 모드**: 메모 없이 **사진만으로** 글을 완성한다. 멈추거나
메모를 요구하지 말 것(사진이 있으면 충분). 비전 단독 모드 원칙:
- **사실은 사진에서만 추출**한다. 메뉴판·간판·가격표·영수증 사진을 꼼꼼히 읽어 **상호명·메뉴명·
  가격**을 확보한다. 사진에 **안 보이는 구체 수치·고유명사·검증 불가한 주장**(정확한 가격,
  "3대째 운영" 등)은 **지어내지 않는다** — 생략하거나 일반화한다.
- **상호명**: 간판/메뉴판 사진에서 읽되, 없으면 작업 폴더명에서 딴다
  (예: `260615_네이다이닝라운지` → "네이다이닝라운지").
- **메뉴·요리**: 외형으로 식별하고(예: 사시미 플레이트, 하이볼) 메뉴판 사진이 있으면 정확한 이름으로 보정.
- **서사·분위기**: 폴더 카테고리(외관/내부/메뉴/디저트)와 실제 사진으로 방문 흐름을 구성. 맛·식감·
  분위기 묘사는 **사진에 보이는 근거**(플레이팅·색감·공간) 위에서 자연스럽게(과장된 단정 금지).
- 사진만으로 **글 종류(맛집/제품리뷰/나들이 등)와 페르소나**를 추론한다.
- 사진조차 주제 파악이 불가능할 만큼 모호할 때만 사용자에게 1줄 확인. 그 외에는 진행.

### 1. 페르소나 확정
글 종류를 판단하고 `personas/<글종류>.md` 를 읽는다(말투·구조·사진 배치 패턴).
메모가 없으면 §0 대로 **사진만으로** 종류·페르소나를 추론한다.

### 2. ⭐ 사진 분석·태깅 (Opus 4.8 비전) — 가장 중요
`data/input/<job>/photos/` **하위 카테고리 폴더까지 재귀로** 모든 사진을 직접 열어(Read) 무엇이 찍혔는지 파악한다.
파일명/촬영 순서가 아니라 **실제 이미지 내용**으로 판단하되, **상위 폴더 이름**(예: `메뉴`, `쿠로타마네기`)을
카테고리 추론의 출발점으로 삼는다. 폴더명과 실제 내용이 어긋나면 내용 우선.

각 사진을 태깅해 `data/drafts/<job>/photo_tags.json` 으로 저장:
```json
{
  "job": "<job>",
  "model": "opus-4.8-vision",
  "photos": [
    {
      "file": "IMG_9923.JPG",
      "category": "외관",              // 외관 | 내부 | 메뉴음식 | 음료 | 디저트 | 인물상황 | 디테일 | 기타
      "subject": "블랙 우드 외관 전경",  // 무엇이 찍혔는지 한 줄
      "hero": true,                     // 단독 대표샷 후보면 true
      "representative": true,           // ⭐ 글 전체를 가장 잘 대표하는 '딱 한 장'(썸네일감)이면 true
      "group_key": "외관"               // 같은 group_key 끼리 한 그룹(콜라주) 후보
    }
  ]
}
```
- `category`/`subject` 가 **본문 어디에 들어갈지** 결정하는 근거가 된다.
- 흐림·중복·실패 컷은 `category:"기타"` 로 표시하고 배치에서 빼도 된다(왜 뺐는지 남길 것).
- 같은 메뉴/같은 공간 여러 컷은 같은 `group_key` 로 묶는다.
- `representative` 는 **photo_tags.json 안에서는 네 메모일 뿐**(publish 는 안 읽음). 실제로
  대표가 되는 건 **layout.json 의 단독 블록에 단 `representative:true`** 다(§3, §5). 둘을
  **같은 파일**로 일치시켜라. 대표 후보는 페르소나의 **`3-4. 대표 이미지 선정 기준`** 을 따른다.

### 2.5 영상(MOV/MP4) → GIF (영상이 있을 때만)
네이버 글에는 **GIF 움짤**로 넣는다(영상 직접 첨부 X). 분업: **Python 이 프레임 추출·GIF 렌더(기계),
너는 "어떤 영상을 쓸지·어디서 어디까지 자를지"만 결정(인지).** 영상 원본은 **절대 통으로 열지 말 것**(토큰 폭증).

**절차**
1) (사용자/사전단계) `python main.py video-scan --job "<job>"` 실행 → 분석용 썸네일이
   `data/drafts/<job>/video/frames/<key>/frame_NNN_tSS.SS.jpg` 로, 매니페스트가
   `data/drafts/<job>/video/videos.json` 로 생성된다(영상당 최대 8장, 가로 480px).
   - 프레임 파일명의 `tSS.SS` 가 **그 프레임의 영상 내 시각(초)** 다. 시간순으로 정렬돼 있다.
   - ⭐ 프레임은 **모션 기반으로 선별**된다(균일 분할이 아니라 **움직임이 큰 구간** 우선). 그래서
     뽑힌 8장 안에 보통 "움직이는 순간"이 이미 들어 있다. `videos.json` 의 `frames[].motion`
     점수(높을수록 그 구간 움직임 큼)를 자를 구간 선택의 보조 힌트로 쓴다(점수 높은 프레임 주변을 노린다).
   - (긴 영상이거나 모션 분석 실패 시 `sample_mode` 가 `uniform...` 로 폴백 — 이땐 균일 8장이라 더 듬성하다.)
   - 프레임이 없으면(스캔 미실행) 멈추고 위 명령을 안내한다.
2) (너) `frames/` 의 프레임들을 **Read 로 직접 보고** 영상별로 판단:
   - ⭐ **"움직여야 사는" 컷만 채택**한다(강아지 움직임, 술 따르기·붓기, 김·연기 피어오름, 불맛,
     면·치즈 들어올리기 등). 그냥 정지된 음식·공간컷은 **GIF로 만들지 않는다**(스킵). 글이 무거워진다.
   - 채택한 영상은 프레임 시각을 근거로 **자를 구간(start 초, duration 초)** 을 정한다. **2~4초** 권장.
     동작이 가장 또렷한 구간을 고른다(애매한 도입/끝 흔들림은 피한다).
3) (너) `data/drafts/<job>/video_plan.json` 작성:
```json
{
  "job": "<job>",
  "clips": [
    {"source": "강아지들/IMG_0245.MOV", "out": "IMG_0245.gif",
     "start": 1.2, "duration": 3.0, "fps": 12, "width": 480,
     "category": "강아지들", "caption": "꼬리 흔드는 댕댕이", "note": "왜 이 구간인지 메모"}
  ]
}
```
   - `source` 는 videos.json 의 `source` 값(카테고리/파일명) 그대로.
   - `out` 은 결과 GIF 파일명(보통 원본 stem + `.gif`; 한 영상에서 **여러 구간**을 쓰면 `IMG_0245_01.gif` 처럼).
   - `fps`/`width` 생략 시 기본 12fps/480px. **움직임 많은 컷(강아지 등)은 width 400~480**, 가로 영상은 540~600 가능.
   - 렌더러가 **6MB 목표 상한**으로 자동 축소(fps→폭 순)하니 용량은 신경 안 써도 된다(품질만 보면 됨).
4) (너) layout.json 에 GIF 를 **일반 단독 이미지 블록처럼** 배치한다(파일명만):
   `{"type":"image","file":"IMG_0245.gif","align":"center","caption":"꼬리 흔드는 댕댕이"}`
   - GIF 는 그 **동작이 어울리는 문단 위치**에 넣는다(예: 강아지 얘기 문단 옆, 술 따르는 묘사 옆).
   - ⚠️ **GIF 에는 `representative:true` 금지**(대표/썸네일은 정지 사진 1장으로 유지 — 움짤 첫 프레임이 썸네일이면 어색).
   - ⚠️ GIF 는 **콜라주 그룹(`files`)에 넣지 말 것** — 항상 **단독(`file`) 블록**으로(움짤은 한 장씩 보여야 산다).
5) (사용자) `python main.py video-render --job "<job>"` → `photos/_gifs/<out>.gif` 생성. **publish 전에** 실행.

> 순서 불변식: `video-scan` → (너의 plan/layout 작성) → `video-render` → `publish`. GIF 는 video-render 까지 끝나야
> 실제 파일이 생기고, publish 검증이 통과한다(없으면 "사진 파일 없음" 에러).

### 3. 사진 배치 계획 (태그 기반)
페르소나의 사진 배치 패턴 + 위 태그로 배치한다:
- **첫 블록**: `hero:true` 중 페르소나에 맞는 **단독 대표샷 1장**(보통 외관/공간 또는 시그니처).
  페르소나가 텍스트 인트로 우선이면 짧은 도입(2~5줄) 뒤 첫 사진.
- ⭐ **대표 이미지(썸네일) 선정**: 글 전체를 가장 잘 대표하는 **딱 한 장**을 고른다(페르소나의
  `3-4. 대표 이미지 선정 기준`). 규칙:
  - **그 사진을 첫 이미지 블록(단독)으로 두고** 그 블록에 `"representative": true` 를 단다.
    네이버는 **맨 위 이미지를 자동으로 썸네일(대표)** 로 쓰므로, 대표를 첫 이미지로 두는 것이
    가장 확실하다(발행기가 별도 클릭 없이 그대로 보존).
  - **딱 한 장만**, 그리고 **단독(`file`) 블록에만** 단다. **그룹(`files`/콜라주) 블록엔 금지**
    (무시되고 경고가 뜬다). 대표로 쓰고 싶은 컷이 콜라주 후보라도, 대표용으로는 **단독 블록**으로 뺀다.
  - 어떤 사진이 대표인지 자신 없으면(특히 메모 없는 비전 단독 모드) **억지로 달지 말 것** — 그냥
    가장 좋은 단독 컷을 맨 앞에 두면 네이버 기본으로 그게 썸네일이 된다.
- **그룹화**: 같은 `group_key`(같은 메뉴·공간) 사진을 묶어 **콜라주** 그룹으로(⭐ 슬라이드 금지 —
  그룹은 항상 콜라주). image 블록 `"layout"` 은 `"콜라주"` 로 쓰거나 생략(생략 시 기본=콜라주).
  페르소나의 **단독/그룹 비율**과 **최빈 그룹 크기**(2/3/4장)를 따른다.
- **순서**: 자연스러운 서사(도착 → 외관 → 공간/내부 → 메뉴 전개(코스 순) → 디저트 → 마무리).
  각 사진의 `category`/`subject` 가 그 위치의 본문 맥락과 맞아야 한다.
- 모든 사진을 빠짐없이 쓰되, 흐림/중복 컷만 제외한다.

### 3.5 장소(지도) 블록 — 상호명 웹검색으로 위치 확정
**물리적 장소가 있는 방문형 글**(맛집/카페/나들이/전시 등)에만 `place` 블록을 **하나** 넣는다.
- **상호 추론**: `description.txt` + job 폴더명(예: `0624 바오 서울`)에서 상호명을 뽑는다.
- ⭐ **웹검색으로 확정**: WebSearch/WebFetch 로 그 상호의 **네이버 플레이스 정식 지점명과 주소**를
  찾는다(지점이 여럿이면 메모·사진의 지역 단서로 특정). 지도가 **엉뚱한 매장**을 가리키면 치명적이다.
  - **지점을 못 고르겠으면(동명 매장 다수 등) 추측하지 말고 사용자에게 질문**한다.
  - 사진·메모·검색으로도 상호를 특정 못 하면 **place 블록을 생략**한다(위치를 지어내지 말 것).
- **블록 형태**(schema 의 place):
  `{"type":"place","query":"바오 서울 성수","name":"바오 서울","address":"서울 성동구 …"}`
  - `query`(필수): 검색창에 칠 문자열 = **상호 + 지역/지점**(결과가 한 곳으로 좁혀지게).
  - `name`(선택): 표시·결과 매칭용 정식 상호. `address`(선택): 발행 전 사람이 위치를 검토하도록 기록.
  - ⚠️ `address` 는 **검색으로 확인된 실제 주소만**. 모르면 비워둔다(날조 금지).
- **배치 위치**: 페르소나에 맞는 자리(보통 도입/외관 사진 근처 또는 글 끝 정보 섹션).

### 4. 본문 작성 (~2000자, 페르소나 말투)
페르소나의 **글 구조·어미·추임새·문장 길이**를 그대로 반영한다.
- 길이 목표: **약 2000자(한국어)**. 분량은 **블록당 풍부한 묘사**(맛·식감·향·분위기의
  구체적 감각 묘사 + 실용 정보)로 채운다.
- ⚠️ 분량을 늘린다고 **짧은 텍스트 블록을 3개 이상 연속**으로 몰지 말 것.
  페르소나 리듬(텍스트 1~2블록 → 이미지 1블록, 이미지 2~3문단마다 1장)을 지킨다.
  → "텍스트 과밀"과 "긴 글"은 다르다. 블록은 몰지 말고, 블록당 내용을 풍부히.
- 대시(`-- — – ㅡㅡ`)와 구분 기호(`·`)는 쓰지 않는다(네이버가 글 위에 가로선을 만든다).
  나열·연결은 쉼표, '와/과', 줄바꿈으로.
- ⭐ **줄바꿈(모바일 우선)**: 블로그는 대부분 **모바일**로 읽힌다. 페르소나의 **줄바꿈/문단 형식**
  (`2. 글 구조 → 줄바꿈/문단 형식`: 한 줄당 문장 수·문단당 줄 수·문단 사이 빈 줄)을 그대로 재현한다.
  - 줄바꿈은 **텍스트 블록 `content` 안의 `\n`** 으로 표현한다(발행기가 `\n` 을 줄바꿈으로 입력).
    예: `"오늘은 성수 다녀왔어요.\n날씨가 딱 좋더라구요 ㅎㅎ"`. **블록을 쪼개지 말 것** —
    줄바꿈은 한 블록 안에서(위 "텍스트 3블록+ 연속 금지" 규칙과 양립).
  - 모바일 화면에서 **한 줄이 길어지지 않게**: 페르소나가 1문장 1줄이면 그렇게, 문단은 짧게.
- (메모 없는 **비전 단독 모드**) 사진에서 **확인되지 않는** 가격·고유명사·구체 수치를 단정하지 말 것.
  보이는 것은 풍부하게 묘사하고, 모르는 것은 일반화한다(§0).

### 5. 산출물 — 세 파일(서로 일치) + 영상 있으면 네 번째
- `data/drafts/<job>/photo_tags.json` — 위 사진 분석 태그
- `data/drafts/<job>/post.md` — 사람이 읽기 좋은 본문. 사진 자리는 `{{photo: 파일명}}`
- `data/drafts/<job>/video_plan.json` — **영상이 있을 때만**(§2.5). 채택한 영상의 자를 구간 목록.
- `data/drafts/<job>/layout.json` — `LAYOUT_SCHEMA` 를 정확히 따르는 배치도(발행이 파싱)
  - 단독: `{"type":"image","file":"a.jpg","align":"center","tag":"외관 전경"}`
  - 대표(첫 단독): `{"type":"image","file":"hero.jpg","align":"center","representative":true,"tag":"외관 전경"}`
  - 그룹: `{"type":"image","files":["a.jpg","b.jpg"],"align":"center","tag":"치킨 스프"}`
  - 장소: `{"type":"place","query":"바오 서울 성수","name":"바오 서울","address":"서울 성동구 …"}` (§3.5, 방문형만)
  - `"tag"` 는 선택 필드(발행기는 무시, 사람 검토·추적용). **`file`(문자열) vs `files`(배열) 혼용 금지** — publisher가 이걸로 단독/그룹을 판별한다.
  - `"representative":true` 는 **단독 블록 하나에만**(썸네일). 가능하면 **첫 이미지 블록**으로. 여러 개 달거나 그룹에 달면 무시되고 발행 시 경고가 뜬다.
  - **파일 지정**: `file`/`files` 에는 **파일명만** 적으면 된다(publish 가 `photos/` 하위 카테고리 폴더까지 재귀로 찾음). 단, **서로 다른 폴더에 같은 파일명**이 있으면 모호해 검증 에러가 나므로 그때만 `"메뉴/IMG_1.jpg"` 처럼 `<카테고리>/<파일>` 로 적는다.

### 6. 해시태그
페르소나대로 마지막 `tags` 블록(보통 8~10개: 지역명 + 카테고리 + 상호명 조합).
